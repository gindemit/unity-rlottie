One frame, too many owners.

The three-slot render pool is an ownership protocol: rlottie renders directly into a slot that cannot be reused until the render thread has finished uploading it. It removes the current publication copy and makes overlap explicit.

Before: 1 render buffer + 1 unsafe staging buffer Implemented: 3 stateful slots Native paths: 1 fewer full-frame CPU copy Managed/WebGL: stay on their existing model
The short answer

What “three slots” buys us

At peak overlap, one slot can be written by rlottie, one can hold the newest completed frame, and one can be owned by the render-thread upload.

0
publication copies after the change

Completion changes slot state; it does not copy the pixels into a second CPU vector.

3
preallocated ownership slots

Enough for Rendering, Ready, and Uploading to coexist without sharing writable memory.

+1F
generic native-path CPU delta

D3D11, OpenGL, and Metal move from two frame-sized CPU buffers to three. D3D12/Vulkan can reuse mapped upload memory and differ.

Important: this is not the same as Texture2D.Apply(). “Apply the change” means adopting the render pool; Apply() is Unity’s managed upload route and remains the fallback.

Engineering impact

What must change

This is an API and lifecycle refactor, not a local replacement of stagingBuffer.

Shared core

Add per-slot metadata: storage, dimensions, stride, version, and Free / Rendering / Ready / Uploading.

Add native acquire/start/complete semantics. Async futures must capture a slot, not the persistent managed pointer in today’s lottie_render_data.

Claim the newest ready slot on the render thread and coalesce older ready frames. Recheck after clearing the queued flag to close the lost-wakeup window.

Make instance removal wait for rendering/upload ownership; no raw queued pointer may outlive its registry entry.

Behavioral contracts

  • Async: if all slots are busy, return backpressure and let the scheduler try later; do not allocate a fourth slot per frame.
  • Sync: wait for a slot to become free unless the public API explicitly adopts frame skipping.
  • Newest frame wins: a ready frame may be replaced before upload, but rendering and uploading slots are immutable.
  • Managed/WebGL: keep external Unity buffer behavior and do not retain GetRawTextureData() views for native pool paths.
  • Resize/restart: create a new pool, retire the old one only after workers and GPU references are safe.

Rendering upside

Removes one F-byte copy per published native frame, lowers publication lock time, and enables render/upload overlap without data corruption.

Expected visual result

No intentional image-quality change. Same BGRA pixels, same sampled texture, and same frame-coalescing policy—only ownership and transfer staging change.

Main risks

Backpressure deadlocks, stale slot reuse, D3D12/Vulkan GPU lifetime mistakes, resize/dispose races, and route confusion between native and managed upload.

Recommended rollout

Safety first, then zero-copy publication

Phase 1 · two-slot mailbox

Replace the unsafe single publication vector with two preallocated CPU slots. Keep the current one publication copy. This adds F persistent bytes to native paths, prevents overwrite during upload, and is the smallest correctness fix.

recommended prerequisite

Phase 2 · three-slot direct render pool

Move slot acquisition ahead of rendering and point rlottie at slot storage. Remove the publication copy. Specialize D3D12/Vulkan storage so their mapped upload regions can be the render slots.

performance end state
Why not jump blindly? The direct pool touches sync and async rendering, native ABI, scheduling, disposal, resize, graphics restart, every native backend, and GPU retirement. The two-slot mailbox isolates the existing correctness bug and provides stress tests that remain useful during phase 2.
Acceptance

How we know it works

Concurrency

Stress concurrent publish/upload, queue saturation, newest-frame coalescing, all-slots-busy backpressure, and the lost-wakeup boundary under ThreadSanitizer where possible.

Lifecycle

Dispose during render and queued upload, resize while busy, pause/resume, domain reload, graphics-device restart, and multiple simultaneous animations.

GPU correctness

D3D12 fences, Vulkan validation and safe frames, OpenGL without BGRA, Metal devices, Gamma/Linear color, and rendered-player pixel changes with managed fallback rejected on native smoke jobs.
