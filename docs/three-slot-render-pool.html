Architecture explainer · validated dev snapshot · 13 Aug 2026

Rasterize cached. Upload in rings.

The final design separates CPU and GPU ownership: rlottie renders into one of two cacheable CPU mailbox slots. D3D12 and Vulkan then make one sequential copy into independent three-slot mapped upload rings. Immediate APIs consume the CPU slot directly.

CPU mailbox: 2 cacheable slots D3D12/Vulkan: separate 3-slot GPU rings Per-frame allocation: none Managed/WebGL: stay on their existing model
The short answer

Why two CPU slots and three GPU slots?

The CPU only needs to overlap rendering with publication/upload copying. Explicit GPU APIs need a deeper ring because submitted copies outlive the CPU call.

2F
plugin-owned native CPU mailbox

One slot may be Rendering while the other is Ready or being consumed. Publication is metadata-only.

3
explicit-API upload regions

D3D12 regions retire by frame fence; Vulkan transfer buffers retire by Unity safe-frame number.

1×
sequential explicit-API CPU copy

Cache-friendly memcpy or row copy replaces catastrophically slow rlottie blending in mapped upload memory.

Key correction: mapped upload memory is excellent for sequential copies but poor for rlottie’s read-modify-write blending. Direct rendering caused Android Vulkan 1024² frames to rise from roughly 11–15 ms to 165–200 ms and Windows D3D12 to fall from about 1393 FPS to 1.2 FPS.

Engineering impact

What changed

The public rendering behavior stays compatible; ownership, retry semantics, and backend storage changed internally.

Shared core

Two cacheable CPU slots carry dimensions, stride, version, storage, and Free / Rendering / Ready / Uploading ownership.

Sync and async rendering acquire a CPU slot. Managed Apply/WebGL routes return ExternalBuffer and keep their Unity-owned memory behavior.

The render thread claims the newest ready slot, coalesces stale ready work, and rechecks after clearing the queued flag.

Backend outcomes distinguish accepted work from retry. A missing D3D12 command context or full explicit ring restores Ready without losing a static frame.

Behavioral contracts

  • Backpressure: if both CPU slots are busy, skip/retry without allocating another frame buffer.
  • Newest frame wins: a ready frame may be replaced before upload, but rendering and uploading slots are immutable.
  • Explicit APIs: CPU ownership ends after the sequential ring copy; GPU ownership ends only at fence/safe-frame retirement.
  • Texture ownership: plugin-owned native paths avoid a managed frame buffer. Unity-owned OpenGL/Vulkan paths retain their raw-data view only for live fallback continuity.
  • Resize/restart: create a new pool, retire the old one only after workers and GPU references are safe.

Rendering upside

Publication becomes metadata-only, render/upload overlap is safe, and rlottie remains in cacheable memory. Immediate APIs have no extra copy; explicit APIs have one sequential copy.

Expected visual result

No intentional image-quality change. Same BGRA pixels, same sampled texture, and same frame-coalescing policy—only ownership and transfer staging change.

Main risks

Retry lost wakeups, stale slot reuse, D3D12 state/fence mistakes, Vulkan safe-frame retirement, GLES channel conversion, and resize/dispose races.

Architecture decision

Why the hybrid design won

Keep: two-slot cacheable mailbox

It prevents publication overwrite, has no per-frame allocation, removes the old publication copy, and gives rlottie fast read/write memory.

implemented CPU ownership

Keep: explicit three-slot GPU rings

They protect submitted D3D12/Vulkan copies until fence/safe-frame completion without forcing CPU rasterization to share GPU upload memory.

implemented GPU ownership
Rejected: a single three-slot pool backed by mapped GPU memory conflated CPU and GPU lifetime. It minimized copies but maximized raster cost. The final architecture keeps the ownership benefit while placing each workload in the memory type it prefers.
Validation

What passed, and what remains

Windows

Unity 2022.3 passed 14/14 rendered-player checks on D3D11, D3D12, OpenGL Core, and real native Vulkan. PlayMode passed 8/8. No D3D12 device removal or pool exhaustion occurred.

Android Vulkan

Samsung SM-N975F/Mali-G76 passed 14/14 at sustained 29–30 FPS (33.4–34.5 ms), with native Vulkan selected and no mailbox/ring exhaustion.

Remaining breadth

Continue Apple Metal, WebGL browser, multiple Android GPU vendors, Gamma/Linear, resize/restart, and supported Unity-version coverage. OpenGL Core's single startup GL error reproduces before this change.
